# 조문.py 진행 현황과 다음 할 일

Oct 8, 2026 · @triunee

## 1. 한눈에 보기

- **빌드 체커(`/api/build`)**: RAG 후보 검색 → Rule Engine 판정까지 연결되어 있다. 지금 실력은 held-out v2 기준 규칙 판정 0.83, 최종 빌드 0.81이다 ([평가 기록](evaluation.md)).
- **QA 백엔드(`/ask`)**: 인공지능기본법·시행령 원문을 Qdrant hybrid 검색(dense + sparse, RRF) → 재정렬한 뒤 LLM이 답한다. 개발용 12문항에서 hybrid·재정렬 Hit@3 1.000, MRR 0.917이다. 재정렬을 만들 때 본 질문이라 독립 성능은 아니다.
- **지식그래프**: 적재된 데이터로 만들 수 있는지 검토했고, 규칙만으로 그래프를 만드는 프로토타입을 로컬에서 돌려 봤다. 아직 앱에는 연결하지 않았다 (3장).
- **API 크레딧**: MonoRouter 키 기준 30,000 중 10,737 사용, 19,263 남음 (10월 8일 조회).

## 2. 지금까지 한 일

### 데이터·적재

- 데이터 범위 6종 고정: 인공지능기본법·시행령·영문본, BKL 고영향 가이드라인 해설, 개인정보 보호법, 신용정보법 (`data/sources.json`).
- PDF 6개를 Docling으로 변환해 조·항·호·목 단위 청크 1,769개를 만든다. BKL 해설은 원문 청크 11개와 판정용 요약 9개를 따로 저장한다.
- 수작업 태깅 레코드 152개(`data/tagged/articles.json`)가 Rule Engine 근거, 검색 메타데이터, 평가 정답지를 겸한다. 해설 요약을 뺀 143개는 원문 PDF와 글자 단위로 대조하는 테스트가 있다.

### 빌드 체커

- 특성 추출(LLM 또는 키워드 규칙) → 특성 쿼리로 후보 검색 → 참조 1단계 확장 → Rule Engine 판정 → 제재 경로(DIRECT / INDIRECT / NONE).
- 평가를 검색 · 규칙 · 최종 빌드로 나눠 잰다. held-out v2를 먼저 써 두고 v1 실패 7건을 고쳤다 (v2 최종 빌드 0.53 → 0.81).
- 평가 때 특성을 케이스마다 한 번만 뽑아, 규칙만 모드와 최종 빌드가 같은 추출 결과를 쓰게 했다. `--extractor llm` 모드를 추가했다.

### QA 백엔드

- 서비스 설명이 없으면 조문의 뜻과 확인할 조건만 설명하고, 있으면 Rule Engine 점검 결과를 덧붙인다. 실제로 인용한 청크만 `sources`로 돌려준다.
- sparse 검색에 IDF를 적용했다 (같은 12문항 sparse Hit@3 0.750 → 1.000).

### 지식그래프 검토

- 판단: **만들 수 있다.** 다만 그래프의 재료는 임베딩 벡터가 아니라 청크 메타데이터(조·항·호·목 ID, `lead`)와 태깅 필드(`refs`, `addressee`, `condition`, `penalty`)다. 벡터는 유사 엣지를 추정할 때만 보조로 쓴다.
- 규칙만으로(LLM 없이) 그래프를 만드는 프로토타입을 작성하고, 일부를 잘라 인터랙티브 화면으로 그려 봤다.

## 3. 지식그래프 프로토타입

### 위치

`reference/knowledge_graph/`에 있다. 이 폴더는 `.gitignore`에 넣어 **저장소에 커밋하지 않는 로컬 참고 자료**다.

| 파일 | 내용 |
| --- | --- |
| `build_graph.py` | 그래프 생성 스크립트. 저장소 루트에서 `python reference/knowledge_graph/build_graph.py` |
| `template.html` | 시각화 페이지 틀 (d3-force) |
| `subgraph.json` | 고영향·생성형·국내대리인 축만 잘라 낸 예시 그래프 |
| `kg-example.html` | 예시 그래프를 넣은 페이지. 브라우저로 바로 연다 |

### 스키마

| 노드 | 출처 |
| --- | --- |
| 조문(provision) | 청크 + 태깅 레코드. 기존 청크 ID를 그대로 쓴다 |
| 수범자(actor) | 태깅 `addressee` 6종 |
| 적용 조건(condition) | 태깅 `condition` (고영향 AI인 경우, 생성형 AI인 경우 등 12종) |
| 정의 용어(term) | 제2조 “…”이란 정의 12개 |
| 외부 법률(external) | 본문의 「법명」 중 데이터 6종 밖의 법 |

| 엣지 | 만드는 방법 |
| --- | --- |
| `PART_OF` 상위 조문 | ID 계층 |
| `IMPLEMENTS` 시행령 → 법률 | 시행령 본문 “법 제N조제M항” 정규식 |
| `REFERS_TO` 조문 참조 | 태깅 `refs` + 법률 본문 “제N조” 정규식 |
| `IMPOSES_ON` · `CONDITIONED_ON` · `SANCTIONED_BY` | 태깅 `addressee` · `condition` · `penalty` |
| `DEFINES` · `USES_TERM` | 제2조 정의 + 본문 용어 출현 |
| `CITES` | 「법명」 정규식 |
| `COMMENTS_ON` BKL 해설 → 조문 | 본문 언급 + 키워드 매핑 (추정) |
| `SIMILAR_TO` 시행령 ↔ 법률 | Qdrant 1536차원 벡터 코사인 0.72 이상, 기존 엣지가 없는 쌍만 (추정) |

모든 엣지에 `source`(id / tagged / regex / keyword / embedding)와 근거 문구(`ev`)를 붙였다. 추정 엣지(keyword, embedding)는 판정 근거로 쓰지 않고 검색 확장 후보로만 쓴다.

### 결과 (현재 청크 1,769개 기준)

- 전체 노드 1,741개, 엣지 1,128개. 이 중 PART_OF 567, IMPLEMENTS 112, IMPOSES_ON 102, USES_TERM 95, CITES 95, REFERS_TO 60, CONDITIONED_ON 35, SIMILAR_TO 25, SANCTIONED_BY 15, DEFINES 12, COMMENTS_ON 10.
- 시행령의 “법 제N조…” 언급 122건 중 118건(97%)이 청크 ID로 바로 연결된다. 가장 쓸모 있는 엣지다.
- 예시 그래프는 125 노드 · 284 엣지다. 제31조①(생성형 고지)에서 적용 조건 2개 → 시행령 제23조 → 제43조① 과태료까지 한 화면에서 따라갈 수 있다.

### 확인된 문제

- **엣지 중복**: 태깅 `refs`가 IMPLEMENTS · SANCTIONED_BY · PART_OF와 같은 쌍을 다시 가리키는 경우가 많다. 더 구체적인 엣지가 있으면 일반 참조를 빼도록 정리했다 (1,211 → 1,146).
- **태깅 `domain` 값 혼재**: `SA`, `BA` 같은 목 기호와 `RIGHTS_DECISION`, `ENERGY` 같은 이름이 섞여 있다. 그래프에 영역 노드를 넣으려면 먼저 값을 하나로 정리해야 한다.
- **BKL 해설 연결이 약함**: 판정용 요약 9개에는 조문 언급이 거의 없다. 해설 → 조문 엣지 10개 중 9개를 키워드로 붙였다. BKL 원문은 Qdrant QA 컬렉션에 없어 임베딩으로 연결할 수 없다.
- **Qdrant 버전**: 프로토타입은 로컬 `data/qdrant/`(362포인트, 개정 전 적재)를 읽었다. 앱은 `QDRANT_URL` 서버를 쓰므로, 스크립트도 `app/rag/qdrant_store`의 클라이언트를 쓰도록 바꿔야 한다.
- **Chroma 벡터는 쓸 수 없음**: 빌드 체커의 Chroma는 로컬 해싱 임베딩이라 의미 유사도가 없다.
- PIPA·신용정보법 청크(약 1,180개)는 태깅된 것이 18개뿐이라 구조 엣지만 생긴다. 판정 범위가 원래 일부 조문뿐이라 문제는 아니다.
