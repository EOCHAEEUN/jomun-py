# 평가 기록

> 숫자는 `docs/eval_snapshot.json`과 같습니다. 평가 결과가 바뀌면 `python -m scripts.evaluate --snapshot`으로 스냅샷을 갱신해야 테스트(`test_evaluation_matches_committed_snapshot`)가 통과합니다.

## 무엇을 재나

이전 평가의 `rule_hit = 1.0`은 순환 지표였습니다. Rule Engine이 판정에 쓰는 레코드를 직접 넣고, 그 레코드에 정답 조문이 있는지 본 것이라 검색 성능을 재지 못했습니다. 그래서 파이프라인을 단계별로 나눠 따로 잽니다.

| 단계 | 지표 | 무엇을 보나 |
| --- | --- | --- |
| ① 검색 | Hit@3 — naive | 서비스 설명 그대로 1회 검색했을 때 정답 조문(`gold.retrieval`)이 상위 3개 안에 드는 비율 |
| | Hit@3 — enriched | 설명 + 특성별 법률 용어 쿼리(활용 영역·생체정보·생성형·국외 사업자·자동화된 결정 등), 쿼리마다 상위 3개 |
| | 후보 재현율 · 평균 후보 수 | 실제 파이프라인 후보(쿼리마다 top-5 + 참조 그래프 1단계 확장)에 정답 조문이 들어간 비율. 후보를 무작정 늘려 재현율을 올리지 않았는지 후보 수를 같이 본다 |
| ② 규칙 판정 | 규칙 판정 정확도 | 검색 없이(rules-only) 특성 추출 → Rule Engine 판정이 정답 상태와 맞는 비율 |
| ③ 최종 빌드 | 최종 빌드 정확도 · 케이스 완전 일치 | RAG 후보 → Rule Engine 검증까지 거친 빌드 로그가 정답 상태와 맞는 비율 |

상태 점검 = `gold.statuses`(라벨별 상태) + `gold.absent`(나오면 안 되는 라벨) + `gold.penalty`(제재 경로).
③에서 틀린 점검은 ② 결과로 원인을 나눕니다. ②도 틀렸으면 **특성·규칙**, ②는 맞았는데 ③이 틀렸으면 **검색** 때문입니다.

### 읽는 법

- **v1 1.00은 실력이 아니다.** 실패를 보고 고쳤기 때문이다. 지금 실력은 v2의 ② 0.83, ③ 0.81이다.
- **v2도 완전히 독립적인 평가셋은 아니다.** 수정한 사람이 v2도 썼고 기준선 결과를 본 뒤에 고쳤다. 그래서 v2에서 새로 드러난 실패(아래 표)는 고치지 않고 남겨 두었다. 다른 사람이 쓴 v3로 다시 재는 것이 좋다.
- **후보가 평균 9개쯤 늘었다.** 보강 쿼리 3개(고영향 사전 검토 · 생성형 정의 · 국내대리인 기준) 때문이다. 늘어난 후보 때문에 생긴 오탐(`absent` 위반)은 없다.
- **검색 쿼리를 법률 용어로 바꾸면 검색이 크게 좋아진다.** 서비스 설명 그대로는 정답 조문을 거의 못 찾는다(v1 0.07). 개인정보 보호법·신용정보법 청크가 섞이면서 일상어 설명이 엉뚱한 조문에 붙기 때문이다.
