# 평가 기록

> 숫자는 `docs/eval_snapshot.json`과 같습니다. 평가 결과가 바뀌면 `python -m scripts.evaluate --snapshot`으로 스냅샷을 갱신해야 테스트(`test_evaluation_matches_committed_snapshot`)가 통과합니다.

## 무엇을 재나

이전 평가의 `rule_hit = 1.0`은 순환 지표였습니다. Rule Engine이 판정에 쓰는 레코드를 직접 넣고, 그 레코드에 정답 조문이 있는지 본 것이라 검색 성능을 재지 못했습니다. 그래서 파이프라인을 단계별로 나눠 따로 잽니다.

| 단계 | 지표 | 무엇을 보나 |
| --- | --- | --- |
| ① 검색 | Hit@3 — naive | 서비스 설명 그대로 1회 검색했을 때 정답 조문(`gold.retrieval`)이 상위 3개 안에 드는 비율 |
| | Hit@3 — enriched | 설명 + 특성별 법률 용어 쿼리(활용 영역·생체정보·생성형·국외 사업자·자동화된 결정 등), 쿼리마다 상위 3개 |
| | 후보 재현율 · 평균 후보 수 | 실제 파이프라인 후보(쿼리마다 top-5 + 참조 그래프 1단계 확장)에 정답 조문이 들어간 비율. 후보를 무작정 늘려 재현율을 올리지 않았는지 후보 수를 같이 본다 |
| ② 규칙 판정 | 규칙 판정 정확도 | 검색 없이(rules-only) 특성 추출 → Rule Engine 판정이 정답 상태와 맞는 비율 |
| ③ 최종 빌드 | 최종 빌드 정확도 · 케이스 완전 일치 | RAG 후보 → Rule Engine 검증까지 거친 빌드 로그가 정답 상태와 맞는 비율 |

상태 점검 = `gold.statuses`(라벨별 상태) + `gold.absent`(나오면 안 되는 라벨) + `gold.penalty`(제재 경로).
③에서 틀린 점검은 ② 결과로 원인을 나눕니다. ②도 틀렸으면 **특성·규칙**, ②는 맞았는데 ③이 틀렸으면 **검색** 때문입니다.

### 검색 방식 비교

동일한 청크·쿼리·top-k·평가 기준으로 `/api/build`의 검색 방식만 바꿔 비교했다. RRF는 두 검색의 원점수를 섞지 않고 각 순위의 `1/(60+순위)`를 합친다. 결합 전에는 각 검색에서 `max(4×k, 20)`개를 가져와 최종 k개로 줄인다. 개발 사례의 후보 재현율이 가장 높은 BM25를 기본값으로 선택했다. 상세 사례는 `docs/build_retrieval_compare.json`에 있다.

| 방식 | dev 후보 재현율 / 평균 후보 | held-out v1 후보 재현율 / 평균 후보 | held-out v1 최종 정확도 |
| --- | --- | --- | --- |
| 기존 Chroma | 0.89 / 26.5 | 0.87 / 27.2 | 0.61 (22/36) |
| **BM25 (기본값)** | **0.94 / 27.2** | **0.93 / 28.6** | **0.69 (25/36)** |
| Chroma + BM25 RRF | 0.89 / 26.7 | 0.93 / 28.5 | 0.69 (25/36) |

이 작은 평가셋에서는 BM25가 검색 누락 3건을 줄였지만, 특성 추출·규칙 오류 11건은 그대로다. `BUILD_RETRIEVAL_MODE=chroma|bm25|hybrid`로 방식 변경이 가능하다. BM25는 `chunks.json`에서 인덱스를 만들고, 파일이 바뀌면 다시 만든다.

### 읽는 법

- **검색 쿼리를 법률 용어로 바꾸면 검색이 좋아진다.** 서비스 설명 그대로는 정답 조문을 거의 못 찾는다(held-out 0.07). 특성을 법률 용어 쿼리로 옮기면 0.80까지 오른다.
- **dev 1.00은 실력이 아니다.** 규칙을 만들며 본 케이스라서다. held-out v1의 ②와 ③은 모두 0.69였고, 이제 이 데이터도 비교·분석에 사용됐으므로 새 독립 평가셋이 필요하다.
- **BM25는 검색 누락을 줄였지만 최종 판정의 한계를 없애지 못했다.** 오류 11건은 특성 추출·규칙 단계에 남았다.

## 별도 법률 QA 답변 평가

위 표는 `/api/build`의 검색·규칙 판정 결과다. `/ask`의 **최종 답변**은 별도로 평가했다. 개발에 사용한 기존 QA 질문 12개 대신, 생성 전에 정답 기준을 고정한 새 질문 10개(일반 5개·서비스 5개)에 실제 LLM 답변을 한 번씩 생성했다.

- 질문의 기준일이 빠진 1개를 제외한 **9개 중 전체 답변이 정확한 것은 5개(55.6%)**였다.
- 검색 가능한 9개에서 상위 3개에 정답 조문이 **하나라도** 포함된 것은 8개(88.9%)였지만, 필요한 정답 조문을 **모두** 상위 5개에 찾은 것은 5개(55.6%)였다. 검색은 정답 조문이 없는 문항을 빼고 기준일이 부족한 문항을 포함하므로, 답변 채점의 9개와 문항 구성이 다르다. 검색 Hit 하나가 답변의 근거 완전성을 보장하지 않는다.
- 인용 근거와 대조한 독립 사실 주장 **39개 중 9개(23.1%)는 근거가 부족**했다. 조문과 충돌한 주장은 1개, 법적으로 참일 수 있어도 인용 출처가 뒷받침하지 않는 주장은 8개다. 이 수치를 그대로 허위 사실 발생률로 읽지 않는다.
- 검토자는 Codex AI다. 독립적인 사람이나 법률 전문가의 검수는 아직 없다. 문항 수도 작아 실서비스 신뢰도 추정치로 일반화할 수 없다.
