# 조문.py 기획안

Oct 7, 2026 · @채으님

## 1. 개요

조문.py는 개발하려는 AI 서비스를 한 줄로 입력하면 인공지능기본법상 걸리는 조문을 찾아 **빌드 로그처럼** 보여주는 RAG 기반 Legal Linter다.

- **서비스명:** 조문.py — AI Legal Build Checker
- **한 줄 정의:** AI 서비스 기획을 입력하면 RAG로 관련 조문을 찾고, Rule Engine으로 적용 조건을 판정한 뒤, 조문별 설명과 개발 체크리스트로 보여주는 도구
- **핵심 카피:** 개발자에게 법조문은, 비개발자에게 코드와 같다. → 법조문을 읽는 대신, 법 빌드를 돌린다.
- **데이터 범위:** 인공지능기본법·시행령·영문본, 고영향 AI 판단 가이드라인 해설, 개인정보 보호법, 신용정보법 — 6종으로 고정 (6.0 참고)

* **진행 규모:** 4명이 하루에 끝내는 미니 프로젝트. 뼈대 코드와 태깅 데이터가 있는 상태에서 검수·다듬기·발표에 집중한다.

### 문제 정의

- AI 서비스를 만드는 사람은 대부분 개발자·기획자다. 이들에게 "\~하여야 한다", "대통령령으로 정한다", "\~로 본다" 같은 법률 문법은 비개발자에게 코드만큼 낯설다.
- 기존 법률 챗봇은 조문을 검색해 요약하는 데서 끝난다. 사용자는 "그래서 내 서비스에 뭘 해야 하지?"를 스스로 다시 번역해야 한다.
- 인공지능기본법은 의무 강도(의무·노력의무·재량), 적용 조건(고영향·생성형), 제재 경로(직접·간접·없음)가 조문마다 다르다. 단순 요약으로는 이 차이가 사라진다.

## 2. 타깃 사용자와 핵심 가치

1차 타깃은 AI 서비스를 기획·개발하는 스타트업과 중소기업 실무자다.

| 사용자 | 상황 | 조문.py가 주는 것 |
| --- | --- | --- |
| AI 스타트업 개발자 | 출시 전 법적 리스크를 빠르게 확인하고 싶음 | 조문별 설명과 체크리스트로 의무사항을 파악 |
| AI 서비스 기획자·PM | 기획 단계에서 규제 요건을 기능에 반영해야 함 | 조건부 의무(CONDITIONAL)와 추가 검토 항목(REVIEW) 목록 |
| 해외 AI 사업자 | 국내 출시 시 적용 여부가 불분명함 | 역외 적용(제4조①) → 국내대리인(제36조) 판단 흐름 |
| 공공 납품을 노리는 사업자 | 무엇을 갖추면 유리한지 모름 | 공공기관 우선 고려 요소(OPPORTUNITY) 안내 |

**핵심 가치**

- **번역:** 법률 문법을 MUST / SHOULD / MAY 같은 개발 언어로 바꾼다.
- **개인화:** 조문 검색이 아니라 "내 서비스에 법이 어떻게 적용되는가"를 보여준다.
- **정직함:** 정보가 부족하면 단정하지 않고 되묻거나 REVIEW로 남긴다. 확률 같은 근거 없는 수치는 만들지 않는다.

## 3. 핵심 기능과 사용자 흐름

화면은 서비스 설명 → 점검 결과 → 적용 가이드 3단계로 구성하고, 1차 스캔에서는 ERROR를 띄우지 않는다.

1. **SPEC — 서비스 설명 입력**
   - 예: "얼굴 인식으로 면접 영상을 분석해서 지원자의 채용 점수를 추천하는 AI"
   - &#91;법령 점검\] 버튼으로 스캔 시작
2. **BUILD (1차) — Service Spec Scan**
   - 서비스 설명만 보고 "어떤 조문이 걸리는가"를 판단한다.
   - 사용자가 구현 상태를 말한 적이 없으므로 "미구현" 판정(ERROR)은 하지 않는다.
   - 판정에 필요한 정보가 없으면 되묻는다. 예: "국내에 주소 또는 영업소가 있나요?" (예 / 아니요 / 모르겠어요)
3. **INSPECT — 조문 상세**
   - 점검 결과의 항목을 누르면 적용 조건·설계 질문·구현 작업이 먼저 보이고, 이어서 조문 원문과 적용 이유를 확인한다. 검색·제재 경로는 상세 영역에서 확인한다.
   - 하단에 구현 체크리스트를 제공한다.
4. **BUILD (2차, Stretch) — `--validate`**
   - 사용자가 구현 상태 체크리스트를 입력하면 그때 ERROR / PASS를 판정한다.

**모드 토글 (Stretch — 하루 MVP 밖): `</> Developer` │ `Aa Plain`**

- Developer: `⚠ SHOULD ARTICLE_35_1` 처럼 개발 언어로 표시
- Plain: "권고 수준의 확인사항 — 고영향 AI를 제공한다면 기본권 영향평가를 하도록 노력해야 합니다"처럼 쉬운 말로 표시
- 원문은 두 모드 모두 항상 함께 보여준다.

**최종 리포트:** 검색된 조문 목록과 Knowledge Base 범위를 요약하고 \[Export Report\]를 제공한다 (Stretch — 하루 MVP는 조문별 결과와 적용 사항 체크리스트까지).

## 4. 판정 상태 체계

조건이 확정되기 전에는 REQUIRED를 띄우지 않고 CONDITIONAL로 두는 것이 상태 체계의 핵심 원칙이다.

| 상태 | 의미 | 단계 |
| --- | --- | --- |
| `✓ MATCH` | 서비스 특성이 조문의 정의·영역과 일치 | 1차 |
| `● REQUIRED` | 조건이 확정된 사업자 의무 (MUST) | 1차 |
| `◐ CONDITIONAL` | 조건이 확정되면 적용되는 의무 (MUST 또는 SHOULD) | 1차 |
| `⚠ SHOULD` | 노력의무 (BEST\_EFFORT) | 1차 |
| `? REVIEW` | 법률 본문만으로 단정 불가 → 되묻기 또는 과기부 확인 요청 | 1차 |
| `✦ OPPORTUNITY` | 공공기관 도입 검토 시 우선 고려 요소, 정부 지원 가능 항목 | 1차 |
| `ℹ INFO` | 해당하지 않는 이유 등 참고 | 1차 |
| `↪ OUT_OF_SCOPE` | 데이터 6종 밖 법률 검토가 필요할 수 있음 (연결 법률을 직접 판정하게 되면서 현재 규칙에서는 쓰지 않음) | 1차 |
| `✗ ERROR` / `✓ PASS` | 구현 상태 입력 후 의무 미이행 / 이행 | 2차 (Stretch) |

**보조 표식** — 판정 상태가 아니라 항목에 덧붙는 표시다.

| 표식 | 의미 | 화면 |
| --- | --- | --- |
| `◈ EXTERNAL` | 세부 기준이 장관 고시·다른 법 시행령 등 데이터 6종 밖 규정에 위임됨 | 적용 가이드의 하위 규정 의존 상자 |
| `ℹ REGULATORY_RISK` | 정부 권한 행사(제40조 사실조사 등) 대상이 될 수 있음 | 근거 체인의 INDIRECT 경로로 표시 (별도 상태 아님) |
| `IF … →` | 조건부 항목의 조건 (`IF HIGH_IMPACT_AI`, `IF 정보주체가 거부·설명 요구` 등) | 빌드 로그 요약 앞 |
| 수범자 | 조문의 주어. 정부·정보주체가 주어인 조문은 사업자 의무로 쓰지 않음 | 적용 가이드의 메타 정보 |

REVIEW가 해소되면 CONDITIONAL은 REQUIRED 또는 SHOULD로 승격된다.

### 대표 빌드 로그 (1차 스캔)

입력: "얼굴 인식으로 면접 영상을 분석해서 지원자의 채용 점수를 추천하는 AI"

```
$ lawcheck ./my_service          # RAG 후보 37개 → 규칙 검증

✓ MATCH        제2조4호사목      채용 판단·평가 관련성
                                 └ 검색 후보 바목 기각: 생체정보를 쓰지만 목적이 범죄 수사·체포가 아님
● REQUIRED     제33조①          고영향 AI 해당 여부 사전 검토 (MUST)
                                 └ Penalty: NONE · 필요 시 과기부 확인 요청 가능 (MAY)
? REVIEW       HIGH_IMPACT_AI    추천이 판단·평가에 해당하는지 추가 검토 → 되묻기
◐ CONDITIONAL  제31조①          IF HIGH_IMPACT_AI → AI 기반 서비스 사전 고지 (MUST)
                                 └ Penalty: DIRECT, 제43조①1호, 3천만원 이하 과태료
◐ CONDITIONAL  제34조①          IF HIGH_IMPACT_AI → 안전성·신뢰성 조치 + 게시·5년 보관 (MUST)
                                 └ Penalty: INDIRECT, 제40조 → 제43조①3호
◐ CONDITIONAL  제35조①          IF HIGH_IMPACT_AI → 기본권 영향평가 (SHOULD)
◐ CONDITIONAL  제30조③          IF HIGH_IMPACT_AI → 사전 검·인증 (SHOULD)
✦ OPPORTUNITY  제30조④          IF HIGH_IMPACT_AI → 공공기관 도입 시 우선 고려 요소
? REVIEW       제36조           국내 주소·영업소 여부 → 되묻기
◐ CONDITIONAL  개인정보보호법 제37조의2   IF 완전히 자동화된 결정 → 기준·절차 공개 (④)
◐ CONDITIONAL  개인정보보호법 제23조      IF 민감정보 해당 → 얼굴 등 생체정보 처리 제한 (◈ EXTERNAL)

──────────────────────────────────────────────
1 match · 1 required · 2 review · 6 conditional · 1 opportunity
```

"얼굴 인식"이라는 단어에도 불구하고 제2조4호**바목**(범죄 수사·체포 목적 생체인식)이 아니라 **사목**(채용)으로 판정하는 것이 이 예시의 핵심이다. 개인정보 보호법은 이제 데이터 6종에 들어 있으므로 얼굴정보 처리를 범위 밖(OUT\_OF\_SCOPE)으로 넘기지 않고 제37조의2·제23조를 조건부로 판정한다.

## 5. 시스템 아키텍처

LLM은 판정하지 않는다. 하루 MVP에서는 특성 추출(②)에만 쓰고(쉬운 말 표현인 Plain 모드는 Stretch), 적용 여부 판정은 Rule Engine(⑤)이 맡는다. RAG(④)는 후보 조문을 찾고, Rule Engine은 그 후보가 서비스 조건에 실제로 적용되는지 검증한다. 제4조·제33조①처럼 늘 확인할 조문은 검색과 상관없이 기본 규칙으로 둔다.

&#91;embedded content: 조문.py 아키텍처 · 사전 준비 4단계 + 실행 7단계\]

정보가 부족하면 Rule Engine이 확률을 지어내지 않고 사용자에게 되물어 ①로 돌아가며, 사전 준비 단계의 태깅 JSON 하나가 검색·규칙·평가에 모두 쓰인다.

## 6. 데이터 설계

조문을 절(clause) 단위로 태깅한 JSON이 판정 후보의 Chroma 메타데이터, Rule Engine 입력, 평가셋 정답지를 겸한다. BKL 해설 PDF 원문 청크는 별도 ID로 저장해 요약 레코드와 구별한다.

### 6.0 데이터 범위 (6종 고정)

| 문서 | 근거 | 역할 |
| --- | --- | --- |
| 인공지능기본법 | 법률 제20676호, 2026.1.22. 시행 | 핵심. 조문 태깅·판정 기준 |
| 인공지능기본법 시행령 | 대통령령 제36053호, 2026.1.22. 시행 | '대통령령으로 정한다'로 비어 있던 기준을 채움 (EXTERNAL 해소) |
| 고영향 AI 판단 가이드라인 해설 | 법무법인 태평양, 2025.9.29. (2차 자료) | PDF 원문을 Docling으로 청킹·임베딩하고, 고영향 판단용 요약 9개를 별도 태깅 |
| 개인정보 보호법 | 법률 제21445호, 2026.9.11. 시행 | 제37조의2 자동화된 결정, 제23조 민감정보 |
| 신용정보법 | 법률 제21445호(타법개정), 2026.9.11. 시행 | 제2조제14호 자동화평가, 제36조의2 설명·이의제기 |
| 인공지능기본법 영문본 | 국가법령정보센터 영문 번역 (참고용) | INSPECT 원문 탭에 English 병기 |

이 6종 밖의 규정(장관 고시, 정부가 발표한 고영향 AI 판단 가이드라인 원문 — 위 BKL 해설과는 별개 —, 개인정보 보호법 시행령 등)이 필요한 판단은 EXTERNAL로 남기고 판정하지 않는다. **사람이 실질적으로 개입하는가**는 세 법의 판단에 모두 영향을 주지만 작동 방식이 다르다. 개인정보 보호법(완전히 자동화된 결정)과 신용정보법(종사자 비관여 자동화평가)은 정의상 사람이 개입하면 대상이 아니지만, AI기본법은 본문에 그런 제외 규정이 없어 REVIEW로 남는다.

### 6.1 청킹 원칙

- 고정 길이가 아니라 조 → 항 → 호 → 절 단위로 자른다. 각 청크 앞에 부모 맥락("제34조(고영향 인공지능과 관련한 사업자의 책무) ①항 1호 –")을 붙인다.
- 한 문장에 의무 강도가 둘 이상이면 "하며 / 하고 / 다만"에서 절을 나눈다. 예: 제33조①은 "검토하여야 하며(MUST)" + "요청할 수 있다(MAY)"의 두 절이다.
- PDF 머리말·꼬리말("법제처 N 국가법령정보센터")은 문장 중간에 끼어들므로 정규식으로 먼저 제거한다.
- 여섯 PDF를 Docling native 파서로 읽는다. BKL 해설 PDF 원문은 페이지별 청크로 저장하고, Rule Engine 후보 검색은 검수된 요약 9개를 사용한다.
- 태깅 범위: 인공지능기본법 66개(제2·4·16③·17③·30\~36·40·43조), 시행령 59개(제2·23\~29조), 신용정보법 11개, 개인정보 보호법 7개, 가이드라인 해설 요약 9개 — 총 152개. 해설을 뺀 143개는 원문 PDF와 글자 단위로 대조한다. 이 대조 테스트는 적재에 쓰는 Docling과 별개로 pypdf로 텍스트를 다시 뽑아 비교하므로, Docling 변환 결과에 기대지 않고 확인할 수 있다.

```json
  "text": "고영향 인공지능에 해당하는지 사전에 검토하여야 하며",

  "status_rule": "REQUIRED",

  "refs": ["ARTICLE_2_4", "ARTICLE_33_3", "ARTICLE_33_4"],

```

| 필드 | 값 | 비고 |
| --- | --- | --- |
| `addressee` | AI\_BUSINESS / GOVERNMENT / PUBLIC\_AGENCY / COMMITTEE / DATA\_HANDLER / DATA\_SUBJECT / CREDIT\_EVALUATOR / OTHER | 주어(수범자). 사업자 의무로 쓰는 것은 AI\_BUSINESS · DATA\_HANDLER(개인정보처리자) · CREDIT\_EVALUATOR(개인신용평가회사등). DATA\_SUBJECT(정보주체)의 권리는 '요구가 오면 대응'으로 바꿔 표시 |
| `obligation` | MUST / MUST\_NOT / SHOULD / MAY | 누가 무엇을 해야 하는가 |
| `external_dependency` | null / PRESIDENTIAL\_DECREE / NOTICE / GUIDELINE / COMMITTEE | 판단에 하위 규정이 필요한가 (obligation과 별개 축) |
| `condition` | IF\_HIGH\_IMPACT\_AI, IS\_GENERATIVE\_AI, NO\_DOMESTIC\_OFFICE 등 | CONDITIONAL 판정의 근거 |
| `status_rule` | MATCH / REQUIRED / SHOULD / REVIEW / OPPORTUNITY / INFO / REGULATORY\_RISK(보조 표식) | 조건 충족 시 표시 상태 |
| `penalty.type` | DIRECT / INDIRECT / NONE | MUST라고 반드시 제재가 있는 것은 아님 |

개발사업자 / 이용사업자 구분은 `addressee`가 아니라 서비스 특성(`business_type`)으로 둔다. 제31\~36조의 주어는 모두 "인공지능사업자"이기 때문이다.

적재할 때는 모든 청크(태깅 여부와 상관없이)에 원본 추적 필드를 붙여 Chroma 메타데이터로 저장한다.

| 필드 | 값 | 비고 |
| --- | --- | --- |
| `source_file` | `data/raw/`의 원본 파일명 (예: `ai_basic_act_20260122.pdf`) | 청크가 어느 PDF에서 나왔는지 |
| `source_sha256` | 원본 PDF 파일의 SHA-256 해시 | 원본 파일이 바뀌면 값이 달라지므로, 적재 당시 어떤 판본을 썼는지 확인할 수 있다 |

BKL 해설은 ID로 원문과 요약을 구별한다. PDF 원문 청크는 `BKL_P{페이지}_{순번}`(11개, 검색 전용), 판정용 요약 레코드는 `BKL_TWO_STEP`·`BKL_RECRUIT` 같은 의미 ID(9개, `verbatim: false`)를 쓴다.

### 6.3 법률 문법 패턴

어미 변화("하여야 한다 / 하여야 하며", "정한다 / 정하는")를 잡기 위해 어간 기준 정규식을 쓰고('한다'의 첫 글자는 '하'가 아니라 '한'이므로 (한|하)로 둘 다 잡는다), 문자열 순서가 아니라 우선순위로 매칭한다.

```python
LEGAL_PATTERNS = [
    (r"노력하여야\s*(한|하)",       "SHOULD",          100),
    (r"하여서는\s*아니\s*(된|되)",  "MUST_NOT",        100),
    (r"그러하지\s*아니(한|하)",     "EXCEPTION",       100),
    (r"대통령령으로\s*정(한|하)",   "EXTERNAL_DECREE", 100),
    (r"하여야\s*(한|하)",           "MUST",             90),
    (r"로\s*본다",             "TREAT_AS",         90),
    (r"고시(한|하)",                "EXTERNAL_NOTICE",  80),
    (r"할\s*수\s*있",          "MAY",              80),
]
```

- 의무 강도 패턴(MUST, SHOULD 등)과 외부 의존 패턴(EXTERNAL\_\*)은 서로 다른 필드에 기록한다. 예: 제34조② "장관은 … 고시하고"는 장관의 행위이자, 사업자 입장에서는 NOTICE 의존성이다.
- `TREAT_AS` 대표 예: 제34조③ — 다른 법령에 따라 준하는 조치를 이행했으면 이행한 것으로 본다.

| --- | --- | --- | --- |
| 제31조① 사전 고지 | MUST | DIRECT | 제43조①1, 3천만원 이하 과태료 |
| 제36조① 국내대리인 지정 | MUST | DIRECT | 제43조①2, 3천만원 이하 과태료 |
| 제31조②③ 생성물 표시 | MUST | INDIRECT | 제40조① 사실조사 → 제40조③ 시정·중지명령 → 불이행 시 제43조①3 |

## 7. 판정 규칙

판정은 LLM이 아니라 Rule Engine이 하고, 정보가 부족하면 단정 대신 질문이나 REVIEW로 처리한다.

### 7.1 Scope Check (가장 먼저)

- **제4조① 역외 적용:** 국외 사업자라도 국내 시장·이용자에 영향이 있으면 적용 → 제36조 국내대리인 검토로 이어짐
- **제4조② 적용 제외:** 국방·국가안보 목적으로만 개발·이용되는 AI → `REVIEW` + `EXTERNAL`(대통령령으로 정하는 범위 확인 필요)

### 7.2 고영향 AI 판정

- 제2조제4호는 "생명·신체·기본권에 중대한 영향 우려" **AND** "가\~카목 영역"의 두 조건이다. 가이드라인 해설도 1단계(영역) → 2단계(중대한 영향·위험 우려)로 판단한다.
- 목적(purpose) 특성으로 목을 가른다. `biometric=true`라도 목적이 범죄 수사·체포가 아니면 바목이 아니다.
- AI 결과가 사람의 실질적 검토 없이 그대로 판단·평가로 쓰이면 고영향(MATCH). 가이드라인 해설의 채용 해당 사례가 "실질적인 인사권자의 개입 없이" 지원자를 탈락시키는 경우다.
- 사람이 실질적으로 검토해 최종 결정해도 `REVIEW`로 남긴다. 해설은 "실질적인 인사권자의 개입 **없이**" 탈락시키는 경우를 해당 사례로 들 뿐, 사람이 개입하면 고영향이 아니라고 정하지 않았다(역은 성립하지 않음). 고영향 영역과 관련성이 확인된 서비스에서는 ‘사람이 최종 결정한다’는 사실만으로 INFO로 내리지 않는다. 비해당을 확정하려면 제33조① 확인 요청에 따른 비해당 회신 등 명확한 근거가 필요하다.
- "추천"만 하고 결정 방식을 모르면 `REVIEW`로 두고 되묻는다.
- 카목("그 밖에 대통령령으로 정하는 영역")은 시행령에 별도 규정이 없어 `EXTERNAL`로 남긴다.

| 조문 | 조건 | 조건 확정 전 | 확정 후 |
| --- | --- | --- | --- |
| 제33조① | AI 제품·서비스 제공 | — | REQUIRED |
| 제31조① | 고영향 **OR** 생성형 | CONDITIONAL | REQUIRED |
| 제31조② | 생성형 | — | REQUIRED |
| 제31조③ | 실제와 구분 어려운 결과물 | CONDITIONAL | REQUIRED |
| 제34조① | 고영향 | CONDITIONAL | REQUIRED (+시행령 제27조 게시·5년 보관) |
| 제35조① | 고영향 | CONDITIONAL | SHOULD |
| 제30조③ | 고영향 | CONDITIONAL | SHOULD |

### 7.4 제32조 처리

제32조의 주어는 "인공지능사업자" 전체이므로 이용사업자라도 자동 제외하지 않는다. 대상은 시행령 제24조①의 3요건(학습 누적 연산량 10²⁶ FLOPs 이상, 최첨단 기술, 광범위하고 중대한 위험)을 모두 충족하는 시스템이므로, 이 세 가지를 되묻는다. 연산량 산정 방식은 장관 고시(`EXTERNAL`)다.

### 7.5 정부 권한 조문 (addressee ≠ AI\_BUSINESS)

주어가 장관·정부인 조문은 사업자의 MAY로 번역하지 않는다. 사업자 관점의 의미로 바꿔 보여준다.

- 제40조① 사실조사 → `ℹ REGULATORY_RISK` "위반 의심·신고·민원 시 과기부 사실조사 대상이 될 수 있음"

### 7.6 OPPORTUNITY

"공공조달에서 유리" 같은 단정 대신 "공공기관 도입 검토 시 우선 고려 요소"로 표현한다.

- 제30조④ 국가기관등은 검·인증 받은 고영향 AI 제품·서비스를 우선 고려
- 제35조② 국가기관등은 영향평가를 실시한 제품·서비스를 우선 고려
- 제16조③ 국가기관등은 대통령령으로 정하는 AI 제품·서비스를 우선 고려 (`EXTERNAL`)
- 제17조③ 과기부는 중소기업등의 제34조 조치 이행과 제35조 영향평가를 지원할 수 있음

제30조④·제35조②·제17조③ 신호는 고영향 AI일 때의 이야기라서, 고영향이 아직 확정되지 않았으면 `IF HIGH_IMPACT_AI →` 조건을 붙여 보여준다.

### 7.7 연결 법률과 범위 밖

개인정보 보호법·신용정보법은 "사람이 개입하느냐"가 정의에 들어 있는 조문만 판정한다. 채용·대출·학생 평가·공공서비스 결정처럼 개인에 대한 결정이면 개인정보 보호법 제37조의2를, 대출이면 신용정보법 제36조의2를 함께 띄운다. 두 법의 일반 의무(수집·이용 동의, 안전조치 등)는 이번 판정 범위 밖이다. 권리(MAY)의 주어가 정보주체인 조문(제37조의2①②, 신용정보법 제36조의2①②)은 사업자 의무로 쓰지 않고 "요구가 오면 대응"으로 바꿔 보여준다. 6종 밖 규정이 필요한 판단은 "위반"으로 단정하지 않고 `EXTERNAL`로 표시한다.

### 8.2 비교 실험

| 단계 | 지표 | 방식 |
| --- | --- | --- |
| ① 검색 | Hit@3 — 설명 그대로 vs 특성 쿼리 | 서비스 설명 1회 검색 vs 특성을 법률 용어로 바꾼 쿼리(쿼리마다 상위 3개). 데이터 6종, 전체 청크 1,736개 |
| ② 규칙 판정 | 규칙 판정 정확도 | 검색 없이(규칙만 모드) 특성 추출 → 규칙 판정 |
| ③ 최종 빌드 | 최종 빌드 정확도 · 케이스 완전 일치 | RAG 후보 → 규칙 검증까지 거친 빌드 로그. 틀린 점검은 ② 결과로 원인(검색 / 특성·규칙)을 나눈다 |

**지표**

- 조문 검색 Hit@3 (정답 조문이 상위 3개 안에 있는가)
- 판정 상태 정확도 (MATCH / REQUIRED / CONDITIONAL / REVIEW가 정답과 일치하는가)
- 오판정 수: 확정할 수 없는 것을 REQUIRED로 단정한 횟수, penalty 유형을 틀린 횟수
- 인용 정확도: 답변이 인용한 조·항·호가 실제로 그 내용을 담고 있는가

| ③ 최종 빌드 정확도 | 1.00 | 0.61 |
| ③ 케이스 완전 일치 | 1.00 | 0.36 |

**설명을 그대로 검색하면 정답 조문을 거의 못 찾고(held-out 0.07), 특성을 법률 용어 쿼리로 바꾸면 0.80이 된다.** dev 1.00은 규칙을 만들며 본 케이스라 실력이 아니고, 지금 실력은 held-out ③ 0.61이다. 틀린 점검 14개 중 3개는 검색(에너지 영역 가목 누락), 8개는 키워드 특성 추출, 3개는 규칙 범위 때문이다. 이전 표의 "RAG + Rule Hit 1.0"은 규칙이 넣은 근거에 정답이 있는지 본 순환 지표라 뺐다.

발표의 대표 장면은 01번이다. RAG가 생체정보 쿼리로 바목을 후보로 가져오고, 목적 특성(`purpose=recruitment`, `criminal_investigation=false`)을 쓰는 규칙이 "목적이 범죄 수사·체포가 아님"이라는 이유로 바목을 기각하고 사목으로 판정하는 과정을 INSPECT 화면의 '찾은 경로'로 보여준다.

## 11. 발표 포인트와 기대 효과

발표 제목은 "조문.py — 법조문을 읽는 대신, 법 빌드를 돌립니다"로 하고, 기술 설계의 핵심을 역할 분담 한 문장으로 전달한다.

**핵심 메시지:** LLM은 서비스 특성만 추출하고, Chroma는 후보 조문을 찾고, Rule Engine이 적용 여부를 판정한다. 문법 파서와 정적 템플릿이 법률 문법을 개발자 언어로 변환한다. LLM 기반 쉬운 말 표현은 Plain 모드에서 확장한다.

**대표 데모 3장면**

1. **바목 함정** — "얼굴 인식 채용 AI"가 범죄 수사 생체인식(바목)이 아니라 채용(사목)으로 판정된다. RAG가 후보로 가져온 바목은 규칙이 이유와 함께 기각한다 (평가셋 01)
2. **같은 답, 법마다 다른 판단** — "사람이 실질적으로 검토해 최종 결정해요"를 고르면 개인정보 보호법 제37조의2는 INFO(완전히 자동화된 결정 아님)로 바뀌지만, AI기본법 고영향은 REVIEW로 남고 제34조① 등은 CONDITIONAL로 유지된다. 같은 문장을 법마다 다르게 읽어야 해서 LLM 한 번으로 뭉뚱그리면 안 된다는 장면이다 (평가셋 11)
3. **시행령이 채운 숫자** — 해외 기업 예시에서 제36조 질문에 시행령 제29조 기준(매출 1조 · AI 매출 100억 · 이용자 100만)이 그대로 나온다. 제34조①의 근거 체인(제40조 → 제43조)을 함께 보여준다

**"왜 RAG인가" 예상 질문 대응**

- 법 하나는 컨텍스트에 통째로 넣을 수 있지만, 실제 규제 판단은 시행령·해설·연결 법률로 이어진다. 이번 데이터 6종만 해도 청크가 1,736개다.
- 서비스 설명을 그대로 검색하면 정답 조문을 거의 못 찾는다(held-out Hit@3 0.07). 특성을 법률 용어 쿼리로 바꾸면 0.80이 되고, 규칙은 그 후보만 검증한다.

**기대 효과**

- 개발자·기획자가 법률 문법을 몰라도 자기 서비스의 의무사항을 개발 요구사항 형태로 파악
- 기획 단계에서 고지·설명·감독 기능을 미리 설계에 반영
- 규제뿐 아니라 공공기관 우선 고려 요소, 중소기업 지원 같은 기회 정보까지 제공
