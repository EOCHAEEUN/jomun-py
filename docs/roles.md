# 조문.py 역할 명세

Oct 7, 2026 · @채으님

## 1. 한눈에 보기

하루 동안 4명이 조문.py의 파이프라인을 **데이터 → 판정 → 검색·평가 → 화면** 구간으로 나눠 하나씩 맡는다. 뼈대 코드와 데이터 6종이 이미 있으므로, 하루의 목표는 새로 만드는 것보다 **검수하고 다듬어 데모 3장면을 완성하는 것**이다. 폴더 단위로 주인을 정해 같은 파일을 두 사람이 동시에 고치지 않는다.

| 역할 | 한 줄 미션 | 담당 폴더 (오너) | 핵심 산출물 |
| --- | --- | --- | --- |
| **나** · PM·기획·프론트 | 범위를 지키고, 화면과 발표로 보여준다 | `app/static/`, `README.md`, 기획안 | 데모 시나리오, 발표 자료, 화면 최종본 |
| **A** · 법률 데이터·QA | 법이 실제로 뭐라고 하는지를 데이터로 확인한다 | `data/tagged/`, `data/eval/` | 검수 완료 `articles.json`, 평가셋 dev 15건 + held-out 11건 |
| **B** · 백엔드·Rule Engine | 서비스 특성을 판정 결과로 바꾸는 엔진을 다듬는다 | `app/engine/`, `app/main.py`, `app/schemas.py`, `tests/` | 판정 규칙 보강, 특성 추출 개선, API 응답 고정 |
| **C** · RAG·평가 | 검색이 왜 규칙과 함께 필요한지 수치로 보여준다 | `app/rag/`, `scripts/` | 검색 · 규칙 · 최종 빌드 단계별 결과표 (dev / held-out) |

**데이터 범위는 6종으로 고정한다.** 인공지능기본법(국문·영문), 시행령, 고영향 AI 판단 가이드라인 해설, 개인정보 보호법, 신용정보법. 하루 동안 새 문서는 추가하지 않고, 범위 밖 규정은 `EXTERNAL`로 남긴다.

## 2. 역할 간 인터페이스

A가 만든 법률 데이터가 B의 판정과 C의 검색을 거쳐 나의 화면과 발표로 모인다. 화살에 적힌 결과물이 역할 사이의 '계약'이다.

C가 찾은 실패 사례는 A에게 돌아가고(고칠 때는 held-out v2를 먼저 쓰고 v1을 dev로 옮긴 뒤 수정), 회색지대 판정은 A가 근거를 올리면 내가 결정한다(점선).

## 3. 역할별 상세 명세

### 나 — PM · 기획 · 프론트엔드

**미션:** 무엇을 왜 만드는지 정하고, 그 결과를 화면과 발표로 보여준다.

**담당 범위:** `app/static/`(화면), `README.md`, 기획안, 일정·이슈 보드

**주요 업무**

- 범위 지키기: 데이터 6종 고정, 하루 범위 밖 기능(2차 빌드, Export, Plain 모드)은 하지 않는다
- 판정 결정 로그의 최종 결정 (A가 근거를 정리하면 결정)
- 화면 다듬기: 시안 대비 차이 정리, 법령 라이브러리(데이터 6종) 화면, 일러스트 원본 교체
- 데모 3장면 확정: ① 바목 함정 ② '사람이 최종 결정'을 골라도 법마다 다르게 판단(개인정보 보호법·신용정보법은 INFO, AI기본법 고영향은 REVIEW 유지) ③ 시행령이 채운 숫자(국내대리인 기준)
- 발표 자료 제작, 오후 리허설 진행

**산출물:** 데모 시나리오, 발표 자료, 화면 최종본, 판정 결정 로그

**완료 기준:** 데모 3장면이 화면에서 끊김 없이 재현된다. README의 실행 방법과 화면 캡처가 최신이다.

**포트폴리오 한 줄:** 법률 문법을 개발 언어로 바꾸는 서비스를 기획하고, 판정 상태 체계(CONDITIONAL·REVIEW)와 3단 화면을 설계했다.

### A — 법률 데이터 · QA

**미션:** 법이 실제로 뭐라고 하는지를 정확한 데이터로 만든다. 이 프로젝트의 **정답지**를 책임진다.

**담당 범위:** `data/tagged/`, `data/eval/`

**주요 업무**

- 새로 태깅된 레코드 검수: 시행령 59개, 신용정보법 11개, 개인정보 보호법 7개 — 수범자, 의무 강도, 조건, 요약 문구 (PM과 교차 검토)
- 인공지능기본법 66개 중 판정에 쓰이는 조문(제2·4·31\~36조) 재확인
- 가이드라인 해설 요약 9개가 원문 취지와 맞는지 확인 (원문 문장을 길게 옮기지 않기)
- dev 평가셋 11건 → 15건: 함정 케이스 추가. 시행령 기준(국내대리인 수치)·고지 예외(내부 업무용)는 held-out v1(H06·H09)과 같은 유형이라 held-out v2를 먼저 쓴 뒤 추가
- 회색지대 판단은 근거를 정리해 판정 결정 로그에 올리기

**산출물:** 검수 완료된 `articles.json`, 평가셋 dev 15건 + held-out 11건(v1 그대로), 검수 메모

**완료 기준:** `pytest tests/test_data.py`(원문 PDF 대조)가 통과한다. 평가셋 정답은 PM과 2인 검토를 거친다.

**포트폴리오 한 줄:** 법령을 절 단위로 구조화하고 평가셋 정답지를 설계해 판정 정확도를 측정할 기반을 만들었다.

> 코딩 부담은 가장 적고 꼼꼼함이 가장 중요한 자리. 데이터 QA·데이터 품질 직무를 노리는 팀원에게 맞다.

### B — 백엔드 · Rule Engine

**미션:** 서비스 특성을 판정 결과로 바꾸는 엔진을 만든다. "LLM은 판결하지 않는다" 원칙을 지킨다.

**담당 범위:** `app/engine/`, `app/main.py`, `app/schemas.py`, `tests/`

**주요 업무**

- A가 고친 태깅에 맞춰 `rules.py` 판정 문구와 근거 정리
- 특성 추출 보강: 채용·대출 문장에서 '자동으로 결정 / 사람이 최종 결정' 키워드 추가, OpenAI 키가 있으면 LLM 추출 점검
- `/api/build` 응답 형식을 오전 중에 고정하고 프론트에 공유 (이후 필드는 추가만)
- 새 dev 케이스가 회귀 테스트로 돌도록 pytest 유지 (held-out은 평가 스냅샷으로만 기록)

**산출물:** 판정 규칙 보강, 특성 추출 개선, API 응답 문서(Swagger)

**완료 기준:** pytest가 전부 통과한다. dev 평가셋 회귀 정확도 1.0을 유지한다(merge 기준). held-out은 보고용이라 점수를 맞추려고 규칙을 고치지 않는다.

**포트폴리오 한 줄:** LLM은 특성만 추출하고 판정은 규칙 엔진이 하는 구조로, 법률 판정의 재현성과 설명 가능성을 확보했다.

### C — RAG · 평가

**미션:** RAG가 왜 필요한지를 실험 수치로 증명한다. 발표의 실험 파트를 책임진다.

**담당 범위:** `app/rag/`, `scripts/ingest.py`, `scripts/evaluate.py`

**주요 업무**

- 데이터 6종 적재 점검: 문서별 청크 샘플 확인 (머리말·개정 표시 제거, 영문 조문 매핑)
- 단계별 결과표 정리 — "설명 그대로 검색 0.07 → 특성 쿼리 0.80", held-out 최종 0.61과 실패 원인(검색 / 특성·규칙) 장면 준비
- (가능하면) OpenAI 임베딩으로 같은 실험 1회 더
- 실패 사례를 원인(검색 / 특성·규칙)과 함께 기록해 A에게 넘기기 — 고칠 때는 held-out v2를 먼저 쓰고 v1을 dev로 옮긴 뒤 B가 수정

**산출물:** 발표용 실험 결과표, `data/eval/results.json`, 실험 조건 메모

**완료 기준:** 다시 적재해도 같은 수치가 나온다. 결과표를 오후 리허설 전에 PM에게 넘긴다.

**포트폴리오 한 줄:** 법령 6종을 적재해 RAG가 후보 조문을 찾고 규칙이 검증하는 구조를 만들고, 검색·규칙·최종 빌드를 held-out 평가셋으로 따로 측정했다.

## 4. 협업 규칙

역할 사이의 '계약'(데이터 형식·API 형식)은 오너만 바꾸고, 바꿀 때는 쓰는 사람의 동의를 받는다. 이 규칙 하나로 대부분의 충돌을 막는다.

### 4.1 계약과 변경 규칙

| 계약 | 오너 | 쓰는 사람 | 변경 규칙 |
| --- | --- | --- | --- |
| `articles.json` 필드 형식 | A | B, C | 필드 추가는 자유. 이름 변경·삭제는 B·C 동의 후 |
| `ServiceFeatures` (`schemas.py`) | B | A, C | 필드를 바꾸면 프롬프트·평가셋을 같은 PR에서 함께 수정 |
| `/api/build` · `/api/sources` 응답 형식 | B | 나 | 필드는 추가만. 삭제·이름 변경은 나와 합의 후 |
| 평가셋 `cases.json` 정답 | A | B (회귀 테스트), C (실험) | 정답을 바꾸면 판정 결정 로그에 근거를 남김 |
| Chroma 메타데이터 키 | C | B (검색 근거 표시) | 키 추가는 자유. 삭제는 B 동의 후 |

### 4.2 브랜치 · PR

- `main`은 보호하고, 역할별 브랜치에서 작업한다: `feature/ui`, `feature/data`, `feature/engine`, `feature/rag`
- PR은 다른 팀원 1명이 리뷰한다. 머지 조건: pytest 통과(dev 회귀 1.0 + 평가 스냅샷 일치). held-out 점수는 머지 조건이 아니라 보고용
- `articles.json`과 `rules.py`를 함께 건드리는 PR은 A와 B가 모두 리뷰한다
- 판정 결과가 평가셋 정답과 다르면 이슈에 A·B를 둘 다 태그한다. 법 해석 문제인지(A), 규칙 버그인지(B) 먼저 가른다

### 4.3 판정 결정 로그

법률 해석은 곧 제품 결정이다. 회색지대 판단은 A가 근거를 정리하고 내가 결정하며, 아래 형식으로 남긴다. 발표 때 "왜 이렇게 판정했나"에 대한 답이 된다.

| 날짜 | 쟁점 | 근거 조문 | 결정 | 결정자 |
| --- | --- | --- | --- | --- |
| 2026-10-07 | AI가 채용 점수를 '추천'만 하면 판단·평가인가 | 제2조4호사목, 제33조③ | 단정하지 않고 REVIEW + 되묻기 | 나 |
| 2026-10-07 | 이용사업자면 제32조를 제외하나 | 제32조①, 제2조7호 | 자동 제외하지 않고 REVIEW | 나 |

### 4.4 회의

- 아침 10분 킥오프: 범위·데모 3장면·계약 2개(데이터 형식, API 응답 형식) 확인
- 점심 직후 10분 중간 점검: 막힌 것, 계약 변경 예고
- 오후 리허설 2회: 데모 3장면을 실제 화면으로 돌려 본다
