## 1. 프로젝트 방향이 바뀐 과정

처음 조문.py는 AI 서비스 설명을 받아 관련 법령을 점검하는 Legal Linter였다. 팀 미니프로젝트의 공통 요구가 **문서 로딩 → 구조 청킹 → Qdrant 검색 → 검색 개선 → 근거 기반 답변 → 평가**였기 때문에, 주 진입점을 AI 기본법 QA인 `POST /ask`로 넓혔다. 기존 서비스 점검 기능은 `/api/build`에 남기고, `/ask`에서 서비스 설명이 있을 때만 특성 추출과 Rule Engine을 추가한다.

이 선택으로 질문이 세 가지 형태를 가진다.

1. “고영향 인공지능이란 무엇인가요?” — 조문의 뜻과 개발 시 확인할 조건을 설명한다.
2. “면접 영상을 분석해 지원자를 평가하는 서비스를 만들고 있습니다. 해당하나요?” — 서비스 사실을 점검하고 적용 가능성을 설명한다.
3. “고영향 AI란 무엇인가요? 제가 위 서비스를 준비하는데 해당하나요?” — 정의와 서비스 검토를 한 번에 답한다.

서비스 정보가 없는 일반 질문에서 특정 서비스의 의무를 확정하지 않고, 서비스 질문에서도 미확정 조건을 확정 의무로 바꾸지 않는 것이 공통 원칙이다.

## 3. 데이터 처리에서 내린 결정

### 원본 버전 고정

현재 국문 QA 근거는 **인공지능기본법 법률 제21311호(2026-07-21 시행)**와 **시행령 대통령령 제36580호(2026-08-20 시행)**다. 법제처 API에서 내려받은 JSON은 버전 대조용으로 `data/reference/law_api/`에 두고, 실제 청킹·임베딩 입력은 `data/raw/`의 해당 PDF다. [`data/sources.json`](../../data/sources.json)에 문서별 역할과 파일명을 기록했다.

### 청킹과 출처

Docling으로 PDF를 읽은 다음 국문 법령은 조·항·호·목 구조에 맞춰 나눈다. 청크마다 문서명, 조문 ID, 페이지, 원본 파일명, SHA-256을 남긴다. 목처럼 본문이 짧은 조각은 상위 호 문장을 `lead`로 보유한다. 답변에 보이는 조문 원문 `text`와 검색용 문맥은 구분한다.

현재 실행 중인 서버의 저장소 수치는 다음과 같다. [`GET /api/health`](../../app/main.py) 응답과 `data/processed/chunks.json`을 확인했다.

| 용도 | 저장소 | 범위 | 청크 |
| --- | --- | --- | ---: |
| `/api/build` 서비스 점검 | Chroma | 기본법 243, 시행령 152, 개인정보보호법 599, 신용정보법 575, BKL 20, 영문본 180 | **1,769** |
| `/ask` 법률 QA | Qdrant | 기본법 243, 시행령 152 | **395** |

BKL 20개는 PDF 원문 11개와 검수한 판정용 요약 9개다. BKL은 2차 자료로 취급하며 `/ask`의 법령 원문 출처에는 포함하지 않는다. QA용 두 법령과 서비스 점검용 여섯 자료를 **같은 평가 수치로 묶지 않는다.**

## 4. 검색과 답변의 구현

`/ask`는 Qdrant의 dense 의미 검색과 어휘 sparse 검색을 RRF로 결합한다. 필요하면 활용 영역의 법률 용어로 질의를 확장하고, 후보는 조문 번호·핵심어·정의 문장·영역 관련성에 따라 **규칙 기반으로 재정렬**한다. 별도의 학습된 재정렬 모델을 사용했다는 뜻은 아니다.

서비스 설명이 있으면 특성을 추출한 뒤 Rule Engine이 사전 점검한다. LLM은 검색된 원문과 점검 결과를 개발자가 읽기 쉬운 문장으로 설명하며, 답변의 `[S번호]`와 반환된 `sources`가 맞는지 검사한다. `sources`에는 실제로 인용한 조문의 원문·문서명·페이지·파일명이 들어간다. 한 질문에 법 개념과 서비스 설명이 함께 있으면 서비스 부분을 따로 읽고, 앞의 법률 질문은 어휘 검색으로 보강한다.

화면에는 법률 질문과 서비스 점검 입력이 있고, 법령 라이브러리에서는 태깅과 원문 참조에 근거한 관계도를 볼 수 있다. 10/08 서버의 `/api/graph` 응답은 조문 노드 **152개**, 기타 노드 **47개**, 관계 **410개**였다. 이 관계도는 발표 보조 자료이며 QA 검색 성능의 증거는 아니다.

## 5. 실험 결과: 서로 다른 평가를 분리하기

### QA 검색 — 개발용 12문항

개정판 395개 Qdrant 청크에서 얻은 [`data/eval/qa_results.json`](../../data/eval/qa_results.json)의 값이다. 이 질문들은 재정렬을 개발하면서 본 자료다.

| 조건 | Hit@3 | Hit@5 | MRR |
| --- | ---: | ---: | ---: |
| Dense 단독, IDF 적용 전 인덱스 | 0.833 | 0.833 | 0.653 |
| Hybrid + 다중 질의 + 규칙 재정렬, IDF 적용 전 | 1.000 | 1.000 | 0.917 |

두 행은 여러 검색 단계가 한꺼번에 다른 비교다. **어느 한 기법만으로 0.653→0.917이 됐다고 말할 수 없다.** 이후 [`scripts/evaluate_qa.py`](../../scripts/evaluate_qa.py)를 dense → sparse → hybrid → 다중 질의 → 재정렬로 따로 측정하도록 바꿨지만, 새 전체 표는 아직 확보하지 못했다.

기존 dense 벡터를 유지한 채 Qdrant sparse의 IDF만 켰을 때, 같은 12문항의 sparse 단독 결과는 다음과 같았다.

| sparse 조건 | Hit@3 | Hit@5 | MRR |
| --- | ---: | ---: | ---: |
| IDF 전 | 0.750 | 0.833 | 0.618 |
| IDF 후 | 1.000 | 1.000 | 0.667 |

질문별 목록은 [`IDF 전`](../qa_sparse_before_20261008.json)과 [`IDF 후`](../qa_sparse_after_idf_20261008.json)에 있다. 12문항에서 질문 하나의 영향이 크므로 이 차이를 일반 성능으로 주장하지 않는다.

### 서비스 점검 — 별도 dev 11 / held-out 11

[`docs/eval_snapshot.json`](../eval_snapshot.json)의 Chroma 1,769개 청크 평가다. QA Qdrant 12문항과 질문·정답·지표가 다른 실험이다.

| 지표 | dev 11 | 서비스 점검 held-out 11 |
| --- | ---: | ---: |
| 검색 Hit@3, 원문 설명 그대로 | 0.28 | 0.07 |
| 검색 Hit@3, 법률 용어 확장 후 | 0.83 | 0.80 |
| Rule Engine 단독 판정 정확도 | 1.00 | 0.69 |
| 검색 → 규칙 최종 점검 정확도 | 1.00 | **0.61** |

개발 중 본 dev의 1.00은 일반화 성능이 아니다. held-out의 최종 0.61은 검색 누락과 사실 추출·규칙 오류가 남아 있다는 근거다. 이 11개 역시 QA 답변 정확도 평가로 바꾸어 쓸 수 없다.

### 테스트와 서비스 상태

WSL 가상환경에서 `python -m pytest -q` 실행 결과는 **254 passed**였다. 테스트에는 Docling 청킹, 규칙 판정, QA API 형식, 일반·서비스·복합 질문 경로, 인용 번호, 관계도가 포함된다. QA의 LLM 호출은 테스트에서 대체했으므로 254개 통과가 실제 생성 답변의 법률 정확성을 증명하지는 않는다.

## 7. 발표에서 지킬 표현

- **말할 수 있는 것:** Docling으로 현재 지정한 PDF를 청킹했고, QA 395개를 Qdrant에서 검색할 수 있다. 12개 개발 질문에서 hybrid·재정렬 Hit@3은 1.000이었다. 복합 질문은 API 테스트에서 정의와 영역 조문을 함께 반환했다.
- **아직 말할 수 없는 것:** 처음 보는 QA 질문에서도 Hit@3이 1.000이라는 주장, IDF가 hybrid MRR을 높였다는 주장, 새 dense 문맥 임베딩이 실서비스 인덱스에 적용됐다는 주장, 254개 테스트가 실제 LLM 답변의 법률 정확성을 보장한다는 주장.
- **정확한 한계:** 현재 QA 개발셋은 12개이며 재정렬 개발에 노출됐다. 서비스 점검 held-out 11개는 QA held-out이 아니다. 실제 답변 품질은 원문 대조와 사람 검수가 남아 있다.

## 8. 다음 측정 순서

1. QA용 새 held-out을 검색·재정렬 코드를 더 고치기 전에 고정한다. 일반 법률 질문, 서비스 질문, 복합 질문, 시행령 질문, 범위 밖 질문을 포함한다.
2. MonoRouter 임베딩 제한을 확인한 뒤 8002를 잠시 중지하고 `python -m scripts.ingest_qa`로 새 dense 문맥을 재적재한다.
3. 같은 인덱스·질문·K에서 `python -m scripts.evaluate_qa`로 다섯 검색 단계를 측정한다.
4. 실제 `/ask` 답변을 조문 원문과 대조하고 정답성·관련성·근거 충실성·환각 여부를 사람 검수표로 남긴다.
