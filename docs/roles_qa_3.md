# 조문.py 3인 작업명세 — AI 기본법 QA

2026-10-08 기준 · 팀원 3명(A/B/C) · 하루 마무리 일정 예시

## 1. 목표와 현재 상태

**목표:** AI 기본법을 잘 모르는 사용자가 일반 법률 질문이나 자신의 AI 서비스 설명을 입력하면, 원문 근거와 함께 개발자가 이해할 수 있는 답변을 받는 `/ask` 백엔드를 완성하고 평가한다.

| 구분 | 현재 상태 | 이번 작업의 완료 조건 |
| --- | --- | --- |
| 문서 처리 | 인공지능기본법·시행령 PDF를 Docling으로 청킹해 362개를 Qdrant에 적재 | 원본 PDF, 청크 ID, 페이지, 해시를 재검증하고 재적재 절차를 문서화 |
| 검색 | 의미 임베딩 + 어휘 검색 + RRF + 규칙 기반 재정렬 구현 | 같은 질문·같은 임베딩으로 dense와 개선 검색을 비교하고 실패 원인 기록 |
| 답변 | `/ask` 일반/서비스 모드, LLM 답변과 인용 출처 구현 | 조건부 의무·노력의무·서비스별 불확실성을 정확히 표현하고 인용 검증 |
| 평가 | 개발용 질문 12개에서 개선 검색 Hit@5 1.000, MRR 0.917 | **새 held-out**과 사람의 답변 검토로 개발용 수치의 한계 보완 |

현재 12개는 검색 방식을 조정하며 본 **개발용 평가셋**이다. 여기서 1.000이 나왔다고 일반 질문에서도 완벽하다고 발표하지 않는다. 기존 `/api/build`의 Chroma·Rule Engine은 서비스 점검 기능으로 유지하고, 이번 RFP의 주 경로는 Docling → Qdrant → 검색 개선·재정렬 → 근거 기반 LLM 답변이다.

## 2. 3명 배정

| 담당 | 책임 | 수정 파일의 주인 | 제출물 |

별도 PM 없이 **C가 통합과 시연을 진행**한다. A는 법률 표현을 승인하고, B는 검색 실험 조건을 승인한다. 공용 파일은 표의 주인만 수정하고 필요한 변경은 PR에서 협의한다. `app/engine/rules.py`나 특성 추출을 바꾸는 경우 C가 구현하고 A가 법률 근거를 검토한다.

## 3. 담당별 실행 명세

### A — 법률 데이터·평가

1. **새 QA held-out 10문항을 먼저 작성한다.** 일반 법률 질문 5개와 서비스 설명을 포함한 질문 5개로 나눈다. 조문 정의, 고지·표시, 고영향 영역, 노력의무, 시행령 위임, 근거 부족 사례를 포함한다.
2. 각 문항에 `id`, `mode`, `question`, 선택적 `service_description`, `gold_ids`, `must_include`, `must_not_say`, `rationale`를 기록한다. `gold_ids`는 Qdrant의 실제 청크 ID로 대조한다. 특히 “사람이 최종 결정한다 → 고영향 아님”과 “노력의무 → 의무 없음” 같은 금지 결론을 명시한다.
3. `scripts/evaluate_qa.py`가 서비스 설명도 `/ask`에 전달하도록 확장한다. Hit@3/5·MRR, 골든 조문 인용 여부를 자동 기록하고 정답성·관련성·근거 충실성·환각 여부는 사람이 검토할 칸으로 남긴다.
4. 데모 답변과 held-out 답변을 원문과 대조해 `docs/qa_review.md`에 **문장 → 조문 → 판정(정확/수정 필요)**으로 기록한다. 핵심 법률 문구는 C와 2인 검토한다.

**완료 기준:** held-out 정답지가 검색/프롬프트 수정 전에 고정된다. 원문에 없는 확정 의무, 의무 강도 오류, 잘못된 조문 인용이 발견되면 수정 사항을 기록한다. held-out 결과를 보고 정답을 바꾸지 않는다.

### B — Docling·Qdrant·검색

1. 원본 인공지능기본법·시행령 PDF에서 Docling 청크를 재생성하고 문서별 수, 제2조·제31~36조 샘플의 본문·페이지·원본 SHA-256을 대조한다. 청크가 잘못 잘린 경우 재현 가능한 수정만 `preprocess.py`에 반영한다.
2. 동일한 임베딩 모델과 동일한 질문·K로 **dense 기준선과 hybrid+RRF+재정렬**을 비교한다. 개발용 12문항은 조정에 써도 되지만 새 held-out은 마지막에 한 번 평가한다.
3. 누락/오검색 사례마다 질문, 기대 청크, dense 순위, 개선 검색 순위, 원인을 남긴다. 재정렬 점수 규칙을 바꾸면 전후 수치와 부작용을 함께 제출한다.
4. WSL 재적재 명령과 Qdrant 로컬 저장소의 단일 프로세스 제약을 점검한다. 서버 실행 중 적재·평가가 필요하면 `QDRANT_URL` 서버 모드로 전환하거나 서버를 멈춘 뒤 실행한다.

**완료 기준:** `python -m scripts.ingest_qa` 후 `/api/health`가 QA 인덱스 ready와 청크 수를 보여준다. 재적재 후 같은 조건의 검색 결과가 재현되고, 원문·출처 메타데이터가 빠지지 않는다. 개선을 주장할 때는 dense 대비 같은 평가셋의 수치를 함께 제시한다.

### C — QA API·개발자 표현·통합

1. `POST /ask`의 입력(`question`, 선택적 `service_description`, `answers`)과 출력(`answer`, `sources`, `mode`)을 고정한다. `sources`의 `source_id`, `article`, `content`, `document`, `page`, `chunk_id`, `source_file`가 답변의 `[S번호]`와 일치하게 한다.
2. 일반 질문에는 서비스별 Rule Engine 판정을 붙이지 않는다. 서비스 설명이 있을 때만 특성 추출·Rule Engine을 사용하고 `REVIEW`·`CONDITIONAL`을 확정 의무로 바꾸지 않는다.
3. 답변은 “조문의 의미”와 “개발 시 확인할 조건/작업”을 짧고 담백하게 설명한다. `하여야 한다`와 `노력하여야 한다`를 구별하고, 근거가 없는 요구사항이나 예시 코드를 만들지 않는다. 근거 없는 인용 ID는 응답에서 거절한다.
4. 일반·서비스 질문, 빈 질문, 인덱스 부재, LLM 오류, 잘못된 인용을 API 테스트로 확인한다. WSL 실행·환경 변수·세 데모 요청/응답을 `README.md`에 정리한다.

**완료 기준:** `/docs`에서 `/ask`가 보이고 세 데모가 실제 LLM 호출로 작동한다. 인용 표식과 `sources`가 대응하며, 일반 질문은 특정 서비스의 적용 의무를 단정하지 않는다. 기존 `/api/build` 회귀 테스트도 통과한다.

## 4. 역할 간 계약과 합치는 순서

| 주는 사람 → 받는 사람 | 계약 | 확인 방법 |
| --- | --- | --- |
| A → B/C | 문항별 `gold_ids`, 필수·금지 주장 | 실제 Qdrant 청크 ID와 원문으로 교차 검토 |
| B → C | 검색 결과 `id`, `doc`, `ref_label`, `text`, `page`, `source_file`, `source_sha256` | API 응답의 출처 역추적 테스트 |
| C → A | `/ask` 답변·인용 출처와 `mode` | 일반/서비스 문항별 법률 표현 검수 |

1. **A가 held-out을 고정**하고 데모 질문 세 개의 정답 조문을 공유한다.
2. **B가 인덱스와 검색 변경**을 마친 뒤 재적재·비교 결과를 공유한다.
3. **C가 API·답변 표현을 통합**하고 A가 실제 답변을 검수한다.
4. 전원이 `python -m pytest -q`와 검색 평가 결과를 확인한다. held-out을 보고 튜닝이 필요하면 그 결과는 개발 자료로 이동시키고 새 held-out을 만든 뒤 다시 측정한다.

## 6. 최종 시연과 제출 체크

1. **일반 질문:** “고영향 인공지능이란 무엇인가요?” → 제2조제4호 근거, 의미와 설계 확인 조건. 특정 서비스 판정 없음.
2. **의무 강도:** “기본권 영향평가는 의무인가요?” → 제35조① 근거, **노력의무**로 설명.
3. **서비스 설명:** “면접 영상을 분석해 채용 점수를 추천하는 AI를 출시하려면?” → 채용 영역 근거와 추가 확인 사항, 미확정 고영향 의무는 조건부로 설명.

제출물은 WSL 실행 명령, Qdrant 적재 결과, 개발용/held-out 검색 비교표, 실제 `/ask` 응답 세 개와 출처, 답변 검수 기록, 전체 테스트 결과다. `.env`의 API 키는 각자 로컬에서 관리한다.
