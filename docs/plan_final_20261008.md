# 조문.py

**AI 기본법 근거 QA와 서비스 맥락 설명 — 최종 기획안**

2026년 10월 8일 · 3인 팀 미니프로젝트 · 발표 및 구현 기준본

## 1. 한눈에 보는 서비스

**미션:** AI 기본법을 잘 모르는 사용자도 질문만으로 관련 조문의 의미를 이해하고, AI 서비스를 만드는 사람은 개발 전에 확인할 조건을 알 수 있게 한다.

| 항목 | 최종 방향 |
| --- | --- |
| 핵심 결과물 | `POST /ask`가 `answer`와 원문 `sources`를 반환하는 AI 기본법 QA 백엔드 |
| 차별점 | 일반 법률 질문에도 개발자 언어로 설명하고, 서비스 설명이 있으면 기존 특성 추출·Rule Engine으로 적용 가능성을 추가 점검 |
| 공통 RAG 흐름 | Docling 문서 로딩·구조 청킹 → 임베딩·Qdrant → 검색 개선·재정렬 → 근거 기반 LLM 답변 |
| 답변 원칙 | 원문 조문을 인용하고, 확정 의무·조건부 의무·노력의무·검토 필요를 구분 |

기존 조문.py는 서비스 설명을 받아 관련 법령을 점검하는 Legal Linter였다. 이번 최종안은 **AI 기본법 QA를 기본 진입점**으로 삼는다. 사용자가 자신의 서비스를 설명하면 Legal Linter의 장점을 더해 “우리 서비스에서는 무엇을 확인해야 하는가”까지 연결한다.

## 2. 사용자와 두 가지 질문 모드

1차 사용자는 AI 서비스를 기획·개발하는 실무자다. AI 기본법을 처음 읽는 일반 사용자도 법률 질문을 할 수 있다. 두 모드는 같은 `/ask` API와 같은 법령 원문 검색을 사용한다.

| 구분 | 일반 법률 질문 | 서비스 설명을 포함한 질문 |
| --- | --- | --- |
| 입력 예 | “고영향 인공지능이란 무엇인가요?” | “면접 영상을 분석해 채용 점수를 추천하는 AI를 출시하려면?” |
| 추가 처리 | 질문을 법률 용어로 확장해 조문 검색 | 서비스 특성 추출 → Rule Engine 사전 점검 → 관련 원문 검색 |
| 답변 | 조문의 뜻, 적용 조건, 개발 시 확인할 항목 | 관련 영역, 적용 가능성, 추가로 확인할 사실과 구현 작업 |
| 경계 | 특정 서비스의 의무가 확정됐다고 말하지 않음 | `REVIEW`와 `CONDITIONAL`을 확정 의무로 바꾸지 않음 |

개발자 언어는 코드 흉내가 아니다. 답변은 **“조문의 의미 → 개발 시 확인할 조건 또는 작업 → 근거”** 순서로 짧고 담백하게 쓴다. 예를 들어 제35조제1항의 영향평가 실시 자체는 **노력의무**이고, 실시할 때는 인공지능취약계층의 특성을 반영할 수 있도록 해야 한다고 구분한다. 고영향 영역과 관련성이 있는 서비스에서 사람이 최종 결정을 한다는 이유만으로 고영향이 아니라고 단정하지 않는다.

## 3. MVP 기능과 API 계약

### 3.1 질문 입력과 응답

`POST /ask`는 필수 `question`과 선택적 `service_description`, `answers`를 받는다. 서비스 설명을 별도 필드로 넣으면 모드가 명확해진다. “우리 서비스는 …”처럼 질문 안에 설명을 적어도 서비스 모드로 처리한다.

```json
{
  "question": "출시 전에 무엇을 확인해야 하나요?",
  "service_description": "면접 영상을 분석해 채용 점수를 추천하는 AI"
}
```

응답은 RFP 필수 필드인 `answer`, `sources`를 포함하고, 어떤 흐름으로 처리했는지 `mode`를 더한다. 답변의 `[S1]`은 `sources[].source_id`와 대응한다. 각 출처에는 조문 번호, 원문, 문서명, 페이지, 청크 ID, 원본 PDF 파일명이 있다.

```json
{
  "answer": "채용 판단·평가 영역과 관련될 수 있습니다. 실제 사용 방식은 추가 검토가 필요합니다. [S1]",
  "sources": [{"source_id": "S1", "article": "제2조제4호사목", "content": "..."}],
  "mode": "service"
}
```

위 응답은 **형식 예시**이며 실제 API는 Docling 원문 청크의 전체 `content`와 출처 메타데이터를 반환한다. `GET /api/health`는 QA Qdrant 인덱스 상태를 보여준다. 기존 화면의 `/api/build`는 별도의 서비스 점검 경로로 운영한다.

### 3.2 이번 범위

- 인공지능기본법과 시행령 원본 PDF를 근거로 하는 한국어 QA
- 일반 질문과 서비스 질문의 개발자 언어 답변, 출처 연결
- 밀집 검색과 어휘 검색의 결합, 검색 결과 재정렬, 검색·답변 평가
- 기존 Rule Engine을 서비스 질문에만 연결

기존 프런트엔드는 `/api/build` 화면으로 유지한다. 이번 RFP 제출 기능은 `/ask` 백엔드와 API 문서(`/docs`)에서 시연한다. 화면의 QA 통합은 후속 확장으로 둔다.

## 4. 데이터와 시스템 구조

### 4.1 오프라인: PDF를 검색 가능한 근거로 만들기

| 단계 | 구현과 데이터 |
| --- | --- |
| 원본 | `data/raw/`의 인공지능기본법 PDF와 시행령 PDF. QA 근거는 이 두 법령으로 제한 |
| 로딩·청킹 | Docling native PDF 변환 후 조·항·호·목 구조를 보존. 청크에 조문 ID·페이지·파일명·SHA-256 기록 |
| 벡터화 | MonoRouter의 `text-embedding-3-small` 의미 임베딩과 한국어 어휘 sparse 벡터 |
| 저장 | 로컬 Qdrant QA 컬렉션. 현행 판본 기준 인공지능기본법 243개 + 시행령 152개 = **395개 청크** |

법제처 시행일 기준 API JSON은 `data/reference/law_api/`에 버전 확인용으로 보관한다. API에서 내려받은 국문 PDF 두 개는 `data/raw/`에 두고 Docling의 입력으로 사용한다. 적재 명령은 `python -m scripts.ingest_qa`이다. 원본 PDF를 변경하지 않고 Qdrant 인덱스를 다시 만든다. 임베딩 제공자·모델을 바꾸면 같은 명령으로 재적재한다. WSL 로컬 Qdrant는 한 프로세스가 저장소를 열므로 적재·평가할 때 API 서버를 멈춘다.

기존 6종 PDF의 Chroma 인덱스는 `/api/build` 전용이다. 여기에는 개인정보 보호법·신용정보법·영문본·BKL 해설도 있으나, `/ask`의 원문 법령 근거와 혼동하지 않는다. BKL 해설은 2차 자료이며 QA의 법령 원문 출처로 사용하지 않는다.

### 4.2 온라인: 근거를 찾아 답하기

1. 질문을 그대로 검색하고, 법률 용어가 필요한 경우 활용 영역 쿼리를 더한다.
2. Qdrant에서 의미 임베딩의 dense 검색과 어휘 sparse 검색을 실행하고 RRF로 합친다.
3. 조문 번호 일치, 질문 핵심어, 정의 조문, 영역 관련성을 반영해 후보를 재정렬한다.
4. 서비스 설명이 있는 경우에만 특성을 추출하고 Rule Engine의 사전 점검 결과를 추가한다. 점검 결과에 필요한 조문은 Qdrant 원문에서 다시 조회한다.
5. LLM에는 선택된 원문과 사전 점검 결과만 제공한다. 답변의 인용 번호를 검증한 뒤 `answer`와 실제 인용한 `sources`를 반환한다.

현재 재정렬은 별도의 학습된 cross-encoder가 아니라 **규칙 기반 재정렬**이다. 검색 품질 개선은 기법의 이름보다 동일 조건의 비교 실험 결과로 판단한다.

## 5. 근거와 법률 표현의 안전장치

| 상황 | 답변 정책 |
| --- | --- |
| 일반 질문 | 조문의 일반적 의미와 적용 조건 설명. 서비스 사실이 없으므로 해당 서비스의 의무를 확정하지 않음 |
| 서비스 질문 | 사실 특성 추출과 Rule Engine 사전 점검을 사용. 고영향 여부처럼 불명확하면 `REVIEW`와 확인 질문 유지 |
| 조건부 조문 | 조건이 충족되기 전에는 확정 의무로 쓰지 않음 |
| 의무 강도 | “하여야 한다”와 “노력하여야 한다”를 구분. 후자는 노력의무로 표현 |
| 근거 부족 | 내용을 추측하지 않고 확인 가능한 범위를 밝힘. 존재하지 않는 `[S번호]`는 응답에서 거절 |

QA가 인용한 청크는 원본 법령 파일·페이지·청크 ID로 거슬러 올라갈 수 있다. **인용 일치만으로 문장 전체의 법률 정확성이 보장되지는 않는다.** 그래서 평가에 원문 대조와 사람의 답변 검토를 포함한다. 이 서비스는 출시 전 법령 검토를 돕는 도구이며 개별 사건의 최종 법률 판단을 대신하지 않는다.

## 6. 평가 계획과 현재 근거

### 6.1 현재 개발용 검색 결과

개발 중 본 질문 12개를 대상으로 같은 임베딩과 Top-K 조건에서 dense 단독과 개선 검색을 비교했다.

| 검색 방식 | Hit@3 | Hit@5 | MRR |
| --- | ---: | ---: | ---: |
| Dense 단독 | 0.833 | 0.833 | 0.653 |
| Hybrid + RRF + 재정렬 | 1.000 | 1.000 | 0.917 |

개정판 원문으로 바꾼 뒤 검색 지표를 다시 측정한 값이다. 답변의 법률 정확성·인용 충실성은 개정판에 대해 다시 검수해야 한다. 이 수치는 **튜닝에 사용한 개발용 질문**에서 나온 것이므로 새로운 질문에 대한 성능이나 답변 정답률로 발표하지 않는다.

### 6.2 최종 검증

법률 데이터·평가 담당이 검색/프롬프트 수정 전에 새 held-out 10문항을 고정한다. 일반 질문 5개와 서비스 질문 5개에 정답 청크 ID, 반드시 포함할 내용, 말하면 안 되는 결론을 기록한다. 검색은 Hit@3·Hit@5·MRR로 비교하고, 답변은 정답성·관련성·근거 충실성·환각 여부를 사람이 검토한다.

검색 실패는 **정답 청크 누락**, 답변 실패는 **잘못된 의무 강도·확정 표현·인용**으로 나눠 기록한다. held-out을 보고 개선하면 그 문항은 더 이상 독립 평가가 아니므로 새 held-out을 만든 뒤 다시 측정한다. 최종 발표에는 개발용 성능과 독립 평가 결과를 분리해 표시한다.

## 7. 3인 팀 실행 계획

| 담당 | 책임과 산출물 |
| --- | --- |
| A · 법률 데이터·평가 | 새 held-out 작성·봉인, 골든 조문과 금지 결론 검수, 평가 스크립트의 서비스 질문 지원, 실제 답변 원문 대조 |
| B · Docling·Qdrant·검색 | 청크·페이지·해시 검수, 재적재 재현, dense/개선 검색 비교, 오검색 원인과 재정렬 변경 기록 |
| C · QA API·개발자 표현 | `/ask` 입력·출력 계약, 일반/서비스 모드 분리, 의무 강도와 인용 검증, 전체 테스트·WSL 시연 통합 |

**작업 순서:** A가 held-out을 먼저 고정 → B가 검색 변경과 동일 조건 실험 → C가 실제 답변을 통합 → A·C가 법률 문장을 교차 검토 → 전원이 전체 테스트와 데모를 확인한다. 파일별 오너와 상세 완료 기준은 `docs/roles_qa_3.md`를 따른다.

## 8. 발표 장면과 완료 기준

1. **일반 정의 질문:** “고영향 인공지능이란 무엇인가요?” → 제2조제4호 원문과 개발 시 확인할 조건. 특정 서비스 판정 없음.
2. **의무 강도 질문:** “기본권 영향평가는 의무인가요?” → 제35조제1항의 평가 실시 자체는 **노력의무**, 실시 시 취약계층 특성 반영은 별도로 설명.
3. **서비스 질문:** “면접 영상을 분석해 채용 점수를 추천하는 AI를 출시하려면?” → 채용 영역 근거, 고영향 여부의 추가 검토, 조건부 의무를 구분.

제출 시에는 WSL 실행 방법, Qdrant 청크·임베딩 상태, 개발용/held-out 검색 비교표, 세 실제 `/ask` 응답과 출처, 답변 검수 기록, `pytest` 결과를 함께 제시한다. “왜 이 답변인가”를 원문 청크까지 따라가며 설명할 수 있으면 완료다.
